MPI Council Report

Roadmap sequencing · 2026-08-02 · Decision: what ships first

Question

How should we sequence building MPI (My Personal Interviewer) from a working local mock-interview app into a private hosted product — given a large wishlist and a known Start/context bug that replays old interview turns?

Council Verdict

Where the Council Agrees

  • Fix Start/context + branch-on-alter before auth, deploy, Drive, or graphs.
  • Auth (Google allowlist) before any public URL.
  • Drive + resume score/improve are v2 / second product surface.
  • Slice 0 also includes: smart titles, resume filename+datetime, voice pause/play, model picker + errors, resizable + mobile.
  • GitHub early for backup — not a product milestone.

Where the Council Clashes

  • Moat timing: Expansionist wants graph/Drive soon after host; Contrarian/Executor defer or skip in v1.
  • Brand order: landing before auth vs brand+deploy together after auth (all block naked deploy).
  • Schema: First Principles demands parent_interview_id now; others said “branch” without fork semantics.

Blind Spots Caught

  • OpenClaw is localhost-only — breaks on deploy unless redesigned.
  • SQLite → hosted DB migration (not just add user_id).
  • In-memory rate limits fail multi-instance hosting.
  • Observability, PII retention, allowlist admin UX, fork copy-vs-reference.

The Recommendation

  • Phase 0: Kill Start ghost + lineage schema (parent_interview_id) + Slice 0 UX bundle.
  • Phase 1: MPI branding + landing-as-login shell.
  • Phase 2: Google Sign-In, allowlist, admin, per-user rows.
  • Phase 2.5: Deploy prereqs — hosted AI path, DB, persistent rate limits, basics of obs/PII.
  • Phase 3: mpi.tomorrowtools.dev behind auth.
  • Phase 4: Profile + performance graph.
  • Phase 5: Drive + resume improve/score.
One thing first: reproduce Start bug → failing test → branch-on-context-change with parent_interview_id (new opener from new resume/JD; old attempt kept).

Advisor responses

The Contrarian
Kill the ghost first. Auth/Drive/deploy on buggy Start = multi-tenant theater. Order: core trust → brand → allowlist auth → deploy behind auth → profile → Drive last.
The First Principles Thinker
Four jobs. Job 1 on fire (correct practice). Job 2 before any URL. parent_interview_id now or regret at auth migration. Job1 → Job2 → Job3 → Job4.
The Expansionist
Product is private interview OS. Fix trust, then race to career loop (profile graph + Drive resume) after auth+host — that is the moat.
The Outsider
“New resume, old interview” breaks trust. Branch = keep old + child under it. Human titles. Pause voice. Model picker. Domain only after login.
The Executor
Slice 0 this week: Start/branch + titles + resume name + voice + model picker + resizable/mobile. Monday: failing test then ship. Auth later.

Peer review highlights

Peer review consensus
Strongest: D (First Principles) — JTBD + parent_interview_id. Biggest blind spot (most): C — moat race underweights ops. All missed: OpenClaw localhost, SQLite→hosted DB, in-memory rate limits, observability, PII, allowlist UX, fork semantics.
